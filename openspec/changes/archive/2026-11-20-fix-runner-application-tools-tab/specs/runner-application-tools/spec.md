## ADDED Requirements

### Requirement: Runner-backed application Tools tab is read-only

When an application's selected source is schema-backed and its Tools tab is available, the system SHALL present a read-only tools list regardless of whether the runner details have resolved. The tab SHALL hide the “Use all available tools” switch, Manage Tools control, tool-type filters, and warnings that apply only to the hidden management mode. Viewing or searching the tab SHALL NOT change the application or its `mcp` fields. Existing application views SHALL apply the same rule.

#### Scenario: Runner details are loading

- **WHEN** a schema-backed application opens its Tools tab before its runner details have resolved
- **THEN** the tool-management switch, Manage Tools control, and tool-type filters are not displayed
- **AND** no application update is generated by opening the tab

#### Scenario: Runner lookup fails

- **WHEN** a schema-backed application's runner cannot be matched or resolved
- **THEN** the Tools tab does not become editable or add an application-level `mcp` object

#### Scenario: Searching does not mutate the application

- **WHEN** a user searches a runner-backed application's tools
- **THEN** the displayed list is filtered without changing the application or marking it modified

### Requirement: Display the application's effective discovered tools

For a runner-backed application, the system SHALL obtain all effective discovered tool definitions for the persisted application through Core's `GET /v1/toolset/{id}/allowed-tools` contract, which follows upstream pages and applies the resolved schema's allowlist. Public asset application IDs SHALL use their applications resource path; platform and config applications SHALL use their deployment name. An empty runner allowlist SHALL impose no Core name filter. The Tools tab SHALL display only the definitions returned by that contract and SHALL NOT add undiscovered allowlist names as manual tools. Search SHALL filter the displayed tools without imposing additional form validation.

The system SHALL show a loading state during discovery. On discovery failure it SHALL show the existing error notification and SHALL NOT replace the result with an unfiltered discovery response. Discovery and Try Out SHALL refer to the saved application rather than unsaved runner or property edits; the UI SHALL NOT present saved results as though they came from unsaved configuration.

#### Scenario: Empty runner allowlist

- **WHEN** the saved runner has an empty or absent allowlist and discovery returns tools from multiple upstream pages
- **THEN** the Tools tab displays all returned discovered tools without a Core name filter

#### Scenario: Runner restricts tools

- **WHEN** the runner allows only a subset of discovered tools
- **THEN** the tab displays the returned allowed tools and does not display disallowed or undiscovered names

#### Scenario: Search narrows results

- **WHEN** a user enters a search term
- **THEN** the tools list shows only matching returned tools
- **AND** clearing the term restores the effective list

#### Scenario: Search is pending

- **WHEN** a runner-backed application's search input differs from the settled search term during the debounce
- **THEN** the results area shows a loading indicator and announces that tools are being searched
- **AND** the search input remains mounted and focused while previous result state is retained
- **AND** the settled results or empty state appear after the search completes

#### Scenario: Discovery fails

- **WHEN** effective tool discovery fails
- **THEN** the tab shows an error notification and does not display an unfiltered fallback as usable tools

#### Scenario: Unsaved runner or property changes

- **WHEN** a user changes the application's runner or properties without saving
- **THEN** discovery and Try Out refer to the persisted application and the UI does not claim the results reflect those unsaved changes

### Requirement: Existing Try Out remains available for usable tools

The system SHALL retain the existing application Try Out experience for each returned tool when current permissions and application state permit it. It SHALL use the existing application call-tool contract and retain its existing response, error, and loading behavior. The new presentation SHALL NOT grant Try Out to a user for whom it was disabled.

#### Scenario: Try out an available tool

- **WHEN** an authorized user opens Try Out for a returned tool and sends a request
- **THEN** the existing application tool-call action is used and its response or error is shown

#### Scenario: Try Out is restricted

- **WHEN** the existing application view disables Try Out for the current user
- **THEN** the read-only tools presentation does not enable it

### Requirement: Other tools workflows remain unchanged

Direct-MCP applications, toolsets, and MCP containers SHALL retain their existing tool discovery, management controls, selection behavior, search, and Try Out routing.

#### Scenario: Direct-MCP application manages its tools

- **WHEN** an editable application has a direct MCP source rather than a runner schema
- **THEN** its existing use-all switch and tool management remain available according to existing rules

#### Scenario: Toolset manages its tools

- **WHEN** a user opens an editable toolset's Tools tab
- **THEN** its existing selection, filters, management, and discovery behavior remain unchanged

#### Scenario: MCP container tools

- **WHEN** a user views a running MCP container's Tools tab
- **THEN** its existing container discovery and Try Out routing remain unchanged
